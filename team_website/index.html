  • Project Description

    Everyone deserves a voice that feels like their own

    Augmentative and Alternative Communication (AAC) devices give people with speech impairments a way to speak, and text-to-speech (TTS) powers many of them. People use an AAC voice more consistently when it feels like theirs.

    The problem: Languages such as Diné Bizaad (Navajo) and Hopi have few or no speech synthesizers. SynthLang builds the tools to change that, including for people who may soon lose their natural voice.

  • The challenge

    A research tool that stopped working

    Where it stood

    • A legacy Tacotron2 implementation that is no longer maintained and can't run reliably on modern hardware
    • No single workflow for training, deploying and using models
    • No user-friendly interface for generating speech

    What we're building

    A modern, modular system that Dr. Tucker can maintain, so he can focus on his research instead of on fixing software.

High-Level Requirements

Working with Dr. Tucker, we defined requirements for the two halves of the system: a web application for generating speech, and a training pipeline for creating new voice models. These were agreed as the project baseline in our Requirements Specification.

Web application

  • Accept text input and return generated audio
  • Let users choose between different voices and languages
  • Show live progress while audio is being generated
  • Store and serve pre-trained models uploaded by the sponsor
  • Work on both mobile and desktop
  • Be easy for NAU ITS to host and maintain

Training pipeline

  • Let Dr. Tucker create models without advanced software engineering skills
  • Support fine-tuning on small, noisy or incomplete datasets
  • Allow training to be configured without editing source code
  • Make training runs reproducible
  • Show progress, errors and outputs during training
  • Support multiple TTS frameworks, so none is a permanent dependency

Key constraints

  • No GPU hosting. University policy prevents using the high-performance GPU cluster for always-online servers, and there is no budget for cloud GPUs. Inference must run on a standard CPU server.
  • Training happens offline. Models are trained on the sponsor's NVIDIA Titan GPUs and then deployed for inference.
  • Reproducible environments. Dependencies must be pinned so the system keeps working as libraries change.
  • Cross-platform. The system must run on both Linux and Windows.

Envisioned Solution

SynthLang is a web-enabled text-to-speech (TTS) training and inference system. Models are trained offline on the sponsor's GPUs, then deployed to a server where anyone can use them from a browser. The two halves are kept separate so the tool stays usable on ordinary CPU-only hosting.

Web application

  • Enter text, choose a voice or language, and start synthesis
  • Live progress feedback while audio is generated
  • Playback controls and downloadable audio (.wav)
  • Works on mobile and desktop

Training pipeline

  • Validates and preprocesses datasets of paired audio and text
  • Configurable training runs, including fine-tuning
  • Logging, progress monitoring and automatic checkpointing
  • Exports trained models for deployment

Technologies

Coqui TTS

The open-source toolkit at the core of our training pipeline. We chose it because it is open access and supports fine-tuning on the small, incomplete datasets typical of under-resourced languages. Its main drawback is that it is no longer actively maintained, so we isolate it behind a wrapper to keep it replaceable.

PyTorch

The deep learning framework for both training and inference, which keeps model formats consistent between the two environments. Training uses CUDA on the sponsor's NVIDIA Titan GPUs, which gave a 15–17x speedup over CPU in our feasibility tests. For deployment, torch.compile() optimizes inference for CPU-only servers.

FastAPI

The backend web server. It exposes the API endpoints, runs the loaded model, and handles requests asynchronously, so a failed or slow synthesis never freezes a user's browser session. We chose it for its speed, its async support and its low overhead.

HTMX and Jinja2

The frontend. Jinja2 templates deliver pages with HTMX attributes, so there is no separate JavaScript build step to maintain. HTMX polling reports synthesis progress instead of WebSockets, which keeps the server simple and compatible with standard university hosting.

uv

The Python package manager. A uv.lock file pins exact dependency versions so the training and production environments match. This directly addresses the sponsor's original problem: a system that broke whenever its dependencies changed.
